2. TECH STACK, SECURITY & LOGGING
===============================================================================
- TECH STACK: Python 3.11+ (PySide6 GUI) + Supabase/PostgreSQL + Local SQLite (Offline Buffer).
- **ROOT/CEO HYBRID DB SWITCHER:** Protected Panel `[İnfrastruktur Və Baza Ayarları]` for Cloud ↔ Private Server DB switching.

  - Keçid tarixçəsi `audit_logs`-da ayrıca `db_migration_events` cədvəlində saxlanılır.
- **ŞİFRƏLƏMƏ AÇARI İDARƏETMƏSİ:** Fernet master key heç vaxt DB-də və ya config faylında plaintext saxlanılmır. Açar env variable və ya OS-səviyyəli credential store (Windows DPAPI) vasitəsilə təchiz olunur, key-rotation prosedur sənədləşdirilir.
- SECURITY: 100% Parameterized SQL Queries. Passwords hashed (Argon2). Sensitive credentials in DB encrypted via Fernet AES-256 (bax: hər server konfiqurasiyası bölmə 7-də ayrıca şifrələnir).

  * **QORUYUCU QAYDALAR:** `Root` roluna aid bəzi kritik flag-lər (`can_manage_license` — yalnız lokal lisenziya statusuna baxmaq/aktivasiya açarı daxil etmək mənasında, bax bölmə 8 qeydi aşağıda, `can_switch_db`, **`can_manage_plugins`** (ÇATIŞMAZLIQ DÜZƏLİŞİ: bölmə 1-dəki SANDBOX QAYDASI artıq "Yalnız Root/CEO tərəfindən... plugin-lər yüklənə bilər" deyir, amma bu flag əvvəllər burada hardlock siyahısına düşməmişdi — indi əlavə edildi ki, iki bölmə bir-birinə zidd olmasın)) heç vaxt custom rola və ya fərdi override yolu ilə başqa istifadəçiyə verilə bilməz — bu flag-lər sistem səviyyəsində "yalnız Root" kimi hardlock edilir, UI-dan belə seçim seçilə bilməz. **Əlavə olaraq (KRİTİK, ANTI-FRAUD QORUYUCUSU):** `can_verify_returns`, `can_override_return_time`, `can_issue_fines`, **`can_approve_dual_control_override`** (ÇATIŞMAZLIQ DÜZƏLİŞİ: bu flag əvvəllər hardlock siyahısında yox idi — əgər Store Manager-ə override yolu ilə verilə bilsəydi, öz mağazasının Kamera Operatorunun override-larını ÖZÜ təsdiqləyə bilər, bütün Dual-Control mexanizmini mənasız edərdi) flag-ləri heç vaxt — nə custom rol, nə də fərdi override yolu ilə — `Mağaza_Meneceri` və ya `Satıcı` rolundakı istifadəçilərə verilə bilməz; bu, yuxarıdakı DUAL-CONTROL qaydasının (bölmə 3, yuxarı) çevik icazə sistemi tərəfindən yan keçilməsinin qarşısını alır və bölmə 4-dəki 3-addımlı anti-fraud iş axınının əsasını təşkil edən vəzifə ayrılığını (segregation of duties) qoruyur. Bu üç flag yalnız `Kamera_Nəzarətçisi` rolunda və ya Root/CEO-nun yaratdığı, açıq şəkildə "kamera-tipli" işarələnmiş custom rollarda mövcud ola bilər. **Əlavə olaraq (KRİTİK, PRİVİLEGE-ESCALATION QORUYUCUSU):** `can_manage_permissions` HEÇ KİMƏ — `CEO` daxil — verilə bilməz, yalnız `Root`-a məxsusdur (ÇATIŞMAZLIQ DÜZƏLİŞİ: əvvəllər bu, Root/CEO ikisinə də hardlock edilmişdi; "System Permission Registry" konsepsiyasına görə yeni flag YARATMAQ ciddi şəkildə Root-un işidir). `can_manage_positions` isə `Root` VƏ `CEO`-ya verilə bilər (mövcud flag-lərdən yeni rol tərtib etmək), amma bunlardan aşağı heç kimə — nə custom rol, nə fərdi override yolu ilə. - THE 3-STEP LEAVE VERIFICATION (ANTI-FRAUD & FAIRNESS):
  * STEP 1 (İcazə Handshake, ÇATIŞMAZLIQ DÜZƏLİŞİ — RƏSMİLƏŞDİRİLDİ): Employee (including the Store Manager) goes to the store PC, enters their 4-digit PIN, seçir **İcazə Növü** (aşağıdakı CEO-təyin edilmiş kataloqdan, yalnız kateqoriyalaşdırma məqsədilə) və clicks `[İcazə İstəyirəm]` (STEP 2-nin `[Mən Qayıtdım]` düyməsinin simmetrik cütü). Bu klik anı NTP-yə qarşı yoxlanılmış sistem vaxtı ilə `Requested_Time` olaraq rəsmi qeyd olunur — cərimə düsturunun (aşağı) əsasını bu vaxt təşkil edir, qeyri-rəsmi/şifahi "getmə" ANLAŞILMAZ VƏ QƏBUL EDİLMƏZ. Status `🔵 Xaricdə` olur.
  * STEP 2 (The PIN Handshake): Employee returns to the store, goes to the store PC, enters their 4-digit PIN, and clicks `[Mən Qayıtdım]`. **Bu düymə yalnız işçinin aktiv (STEP 1-də açılmış, hələ təsdiqlənməmiş) `🔵 Xaricdə` statusu olduqda görünür/aktiv olur** — əks halda düymə göstərilmir (təsadüfi/səhv klikin qarşısını almaq üçün). Status becomes `🟡 Gözləyir (Kamera Təsdiqi)`.
    - **TIMEOUT QAYDASI:** Status 45 dəqiqədən çox "gözləyir" qalarsa, sistem avtomatik HR_Admin və Store Manager-ə eskalasiya bildirişi göndərir. **(ÇATIŞMAZLIQ DÜZƏLİŞİ — TUTARLILIQ):** Timeout-dan sonra `HR_Admin`/`CEO` (Store Manager YOX — dual-control tiering-ə uyğun) manual olaraq `[Təsdiqlə]`/`[Vaxtı Əllə Təyin Et]` əməliyyatını Kamera Operatoru əvəzinə yerinə yetirə bilər (Morning Check-in-in eyni timeout-nəticə mexanizmi ilə eyni, bax yuxarı) ki, işçi Kamera Operatoru cavab verməyənə qədər `🟡` statusunda sonsuza qədər qalmasın.
  * STEP 3 (Camera Operator Action): The Camera Operator sees this on their KompasOS Dashboard. They check the physical footage separately in **iVMS** (ayrı proqram/monitor, KompasOS-a inteqrasiya OLUNMAYIB).
    - Option A: Clicks `[Təsdiqlə]` (Uses current system time — NTP-yə qarşı yoxlanılmış).
    - Option B: Clicks `[Vaxtı Əllə Təyin Et]`. **VALİDASİYA QAYDALARI:** (1) Daxil edilən vaxt sorğu vaxtından əvvəl ola bilməz, (2) gələcək vaxt qəbul edilmir, (3) səbəb sahəsi (min. 10 simvol) məcburidir, (4) 30+ dəqiqəlik override → dual-control qaydasına düşür.
  * PENALTY LOGIC: `Delay = max(0, Verified_Actual_Time − Requested_Time)`. `Total = Requested + 2 × Delay`. Delay mənfi ola bilməz.
  * Cərimə strictly VERIFIED ACTUAL TIME əsasında hesablanır, operatorun düyməni kliklədiyi vaxt əsasında YOX.
  * AUDIT: Any "Manual Time Override" MUST trigger a mandatory log entry in `audit_logs` including operator ID, employee ID, system time, overridden time, mandatory reason text, and (30+ dəqiqə halında) ikinci təsdiqçinin ID-si.
  * **ETİRAZ (APPEAL) MEXANİZMİ:** İşçi hər cərimə/override-a qarşı 72 saat ərzində etiraz göndərə bilər. Etiraz HR_Admin-ə düşür, qərar audit-lənir, cərimə ləğv/azaldıla bilər amma orijinal qeyd heç vaxt silinmir (yalnız "REVERSED" statusu əlavə olunur).

5. OFFLINE-FIRST & SYNC STRATEGY
===============================================================================
- Local SQLite offline buffer yalnız connectivity yoxdursa aktivləşir; hər yazı `sync_status` (`PENDING`, `SYNCED`, `CONFLICT`) sahəsi ilə işarələnir.
- **Konflikt həlli:** audit-kritik cədvəllər (leave_requests, fines, audit_logs) üçün last-write-wins qəbul edilmir. Konflikt aşkarlandıqda hər iki versiya saxlanılır, `CONFLICT` statusu ilə HR_Admin-ə manual həll üçün göndərilir.
- Sync worker exponential backoff ilə cəhd edir (30s → 2dq → 10dq), hər cəhd `app.log`-a yazılır.
- Şəbəkə: mağaza ↔ Supabase əlaqəsi üçün tələb olunan portlar/VPN tələbi sənədləşdirilir.
- **Failover:** hər mağazada minimum 1 ehtiyat cihaz müəyyən edilir ki, əsas PC sıradan çıxdıqda PIN handshake/Camera Dashboard tam dayanmasın.
- **KİOSK MODE WATCHDOG / AVTOMATİK YENİDƏN-BAŞLATMA (ÇATIŞMAZLIQ DÜZƏLİŞİ):** Mağaza PC-lərində işləyən Kiosk Mode instansiyası üçün yüngül bir watchdog prosesi tətbiq gözlənilmədən çökərsə (crash) onu avtomatik yenidən başladır (son vəziyyət/session-a təsir etmədən) və hadisəni lokal `error.log`-a + (bağlantı varsa) crash-hesabatlılığına (bölmə 8) yazır. Bu, mağaza işçisinin "proqram açılmır" deyə panikə düşüb dərhal sizə zəng etməsinin qarşısını alan sadə, effektiv tədbirdir.

8. LİSENZİYA, DEVELOPER (MASTER) PANELİ & UZAQDAN İDARƏETMƏ (CEO/ROOT ÜÇÜN SATIŞDAN SONRA)
===============================================================================
Məqsəd: KompasOS **lisenziya əsasında satılan** bir məhsuldur — hər müştəri (tenant) ayrıca lisenziya alır. Satışdan sonra hazırlayıcı tərəf (sizin şirkətiniz) bütün tenant-ları mərkəzləşdirilmiş şəkildə uzaqdan idarə edə, lisenziyalaşdıra, yeniləyə və lazım gələrsə bloklaya bilsin.

- **LİSENZİYA MODELİ:** Hər quraşdırma unikal `tenant_id` + lisenziya açarı ilə aktivləşir. Lisenziya açarı mərkəzi lisenziya serverinə qarşı dövri (məs. hər 24 saatda) yoxlanılır. Sistem əvvəlcədən **çox-tenant (multi-tenant)** olaraq nəzərdə tutulub — eyni Developer Panelindən paralel olaraq istənilən sayda müştəri idarə oluna bilər.
- **TƏK SİSTEM, AYLIQ ÖDƏNİŞ-ƏSASLI AKTİVLİK (PLAN/TIER YOXDUR):** Bütün tenant-lar üçün eyni, tam funksionallıqlı sistem işləyir — heç bir Basic/Pro/Enterprise fərqləndirməsi və ya modul-səviyyəli feature-flag məhdudiyyəti yoxdur. Hər tenant-ın aktivliyi sadəcə **aylıq ödəniş statusuna** bağlıdır: ödəniş qəbul edildikdən sonra siz (Developer Panelindən) tenant-ı "Aktiv" olaraq işarələyirsiniz və proqram növbəti dövr üçün işləməyə davam edir.
  * Hər tenant qeydində: `son_ödəniş_tarixi`, `növbəti_ödəniş_tarixi`, `status` (`Aktiv` / `Ödəniş Gözlənilir` / `Deaktiv`).
  * Ödəniş vaxtında olmadıqda tenant avtomatik "Ödəniş Gözlənilir" statusuna keçir və qısa ödəniş-qrace-periodu (məs. bir neçə gün, sizin təyin edəcəyiniz) daxilində tətbiq işləməyə davam edir, lakin "ÖDƏNİŞ TƏLƏB OLUNUR" xəbərdarlığı göstərir.
  * **AKTİVLƏŞDİR / DEAKTİV ET — TƏK DÜYMƏ (SADƏLƏŞDİRİLMİŞ):** Developer Panelindəki hər tenant sətrində **tək bir toggle-düymə** — **`[Aktivləşdir / Deaktiv Et]`** — olur. Tenant "Aktiv" vəziyyətdədirsə düymə ona basdıqda "Deaktiv" edir (tətbiq tenant tərəfdə bağlanır/məhdud "LICENSE_INACTIVE" ekranı göstərir, data itkisi olmadan); tenant "Deaktiv"dirsə eyni düymə "Aktivləşdir" funksiyasını daşıyır və proqramı dərhal geri açır. Bu, ödəniş-qrace-periodu bitdikdən sonrakı manual söndürmə üçün, həm də ödəniş edildikdən sonra geri açmaq üçün eyni, vahid kontrol nöqtəsidir.
- **OFFLİNE GRACE PERİODU:** Lisenziya serverinə çıxış olmadıqda tətbiq dərhal bloklanmır — 7-14 günlük grace period, sonra yalnız "LICENSE_UNVERIFIED" xəbərdarlığı ilə məhdud rejim (data itkisi olmadan).
- **ÜÇ FƏRQLİ MƏHDUD-REJİM STATUSUNUN AYDINLAŞDIRILMASI (ÇATIŞMAZLIQ DÜZƏLİŞİ):** Tətbiqdə bir-birindən tamamilə fərqli səbəbli üç xəbərdarlıq/məhdudiyyət vəziyyəti var, hər biri ayrı işə düşmə şərtinə malikdir və UI-da fərqli mətnlə göstərilməlidir: (1) `TIME_DRIFT_DETECTED` (bölmə 2) — PC saatı NTP-dən 60 saniyədən çox fərqlənəndə, yalnız PIN handshake/override kimi vaxt-kritik əməliyyatları bloklayır; (2) `LICENSE_UNVERIFIED` (yuxarı) — lisenziya serverinə uzun müddət çatıla bilmirsə (bağlantı problemi), tam bloklama olmadan xəbərdarlıq; (3) `LICENSE_INACTIVE` / "ÖDƏNİŞ TƏLƏB OLUNUR" (yuxarı) — ödəniş edilmədiyi üçün siz tenant-ı Developer Panelindən Deaktiv etdiyiniz zaman, tətbiqi tam bağlayır. Bu üç status qarışdırılmamalı, ayrı-ayrı işlənməlidir.
- **`LICENSE_INACTIVE` EKRANININ DƏQİQ MƏZMUNU (ÇATIŞMAZLIQ DÜZƏLİŞİ):** Deaktiv olunmuş tenant-da göstərilən ekran ümumi/qeyri-müəyyən xəta mesajı OLMAMALIDIR — səbəbi ("Aylıq ödəniş edilməyib"), son ödəniş/borc tarixini və ödəniş üçün əlaqə vasitəsini açıq şəkildə göstərməlidir ki, müştəri vəziyyəti dərhal anlasın və sizə "niyə açılmır?" tipli sual göndərməsin. Bu vəziyyətdə tətbiq tam bağlanır (heç bir modul, o cümlədən PIN handshake, işləmir) — bu, qəsdən sərt bir ödəniş-təzyiq vasitəsidir, lakin ekranın özü tam şəffaf olmalıdır ki, təəccüb/çaşqınlıq yaratmasın.
- **UZAQDAN İDARƏETMƏ FUNKSİYALARI / DEVELOPER PANELİ (yalnız sizin — qurucunun — Master Root hesabınız üçün, müştərinin öz CEO/Root rolundan TAM AYRI, ayrıca login/domen üzərindən açılır):**
  * **Tenant Siyahısı & Ümumi Görünüş:** Bütün müştərilərin (tenant) siyahısı — quraşdırma tarixi, ödəniş statusu (Aktiv/Ödəniş Gözlənilir/Deaktiv), son/növbəti ödəniş tarixi, son "check-in" vaxtı bir cədvəldə.
  * Hər tenant üçün tək `[Aktivləşdir / Deaktiv Et]` toggle-düyməsi ilə statusu dəyişmək (bax yuxarı).
  * **Ödəniş Xatırlatmaları:** Növbəti ödəniş tarixinə X gün qaldıqda (məs. 7/3/1 gün) Developer Panelində avtomatik xəbərdarlıq və (istəyə görə) sizin özünüzə e-poçt/bildiriş.
  * Versiya məcburi yeniləməsini uzaqdan tetikləmək — bütün tenant-lara və ya seçilmiş tenant-a.
  * Release notes/changelog-u seçilmiş və ya bütün tenant-lara push etmək.
  * Tenant-üzrə aqreqasiya edilmiş telemetriyaya (aktiv istifadəçi sayı, server sayı, sync sağlamlığı və s.) baxmaq — **heç bir halda işçi PII-sinə uzaqdan çıxış YOXDUR**.
  * **AVTOMATİK XƏTA/CRASH HESABATLILIĞI (ÇATIŞMAZLIQ DÜZƏLİŞİ — DƏSTƏK YÜKÜNÜ ƏN ÇOX AZALDAN ADDIM):** Tətbiqdə baş verən handled/unhandled exception-lar və crash-lər avtomatik, anonimləşdirilmiş şəkildə (heç bir PII, yalnız stack-trace + versiya + anonim tenant ID) Developer Panelinə göndərilir və tezliyə görə qruplaşdırılır. Bu, sizin bir bug-ı müştəri şikayət etməzdən ƏVVƏL görməyinizi və düzəltməyinizi mümkün edir — reaktiv dəstək əvəzinə proaktiv monitorinq.
  * **Dəstək Ticket İdarəetməsi:** Bütün tenant-lardan gələn texniki dəstək mesajları (bax aşağı) mərkəzləşdirilmiş şəkildə, tenant-üzrə ayrı thread-lərlə, SLA/cavab-vaxtı izləməsi ilə burada görünür və cavablandırılır.
- **MÜŞTƏRİNİN ÖZ CEO/ROOT PANELİ (tenant-daxili, ayrı):** İstifadəçi/rol idarəetməsi, DB switcher, server idarəetməsi, plugin idarəetməsi, backup/restore, audit log baxışı, shift/off-day idarəetməsi, **ROOT Control Center (sistem limitləri, Feature Toggles, Permission Registry — yalnız `Root`, bax bölmə 3, ÇATIŞMAZLIQ DÜZƏLİŞİ: bu major əlavə bu siyahıya daxil edilməmişdi)** (bax bölmə 3). Master (sizin) panelə çıxışı yoxdur.
- **`can_manage_license` FLAG-İNİN DƏQİQ ƏHATƏSİ (ÇATIŞMAZLIQ DÜZƏLİŞİ):** Bölmə 3-də göstərilən `can_manage_license` flag-i müştərinin öz CEO/Root panelində **yalnız** cari lisenziya statusuna baxmağa, aktivasiya açarını ilkin quraşdırma zamanı daxil etməyə və "ÖDƏNİŞ TƏLƏB OLUNUR"/"LICENSE_INACTIVE" xəbərdarlıqlarını görməyə icazə verir.
